# تقرير: "خدمة تيك توك مزدحمة الآن… انتظر دقيقة" عند "ابدأ بثاً سريعاً"

## 1) السبب الجذري

**الأول (الواجهة) — أُثبت بالتشغيل:** مراقب الواجهة `tiktokConnectWatcher` يعلن الفشل بعد **30ث ثابتة**، بينما السيرفر
يكمل إعادة المحاولة بالخلفية (وينتظر تراجعه عند 429). النتيجة: بعد 30ث بالضبط تظهر "⛔ خدمة تيك توك مزدحمة… انتظر دقيقة"
والشارة "غير متصل" — حتى لو كان المزود رجع سليماً بعد 10ث (جرّبته). ومسار نافذة "ابدأ بثاً سريعاً" (`homeStartQuickConnect`) لا يعرض
أي تقدّم أصلاً: الشاشة تختفي بعد 20ث والشارة تبقى "غير متصل".

**الثاني (السيرفر) — من قراءة الكود، لا يمكن قياسه على Euler الحقيقي (الشبكة محجوبة ببيئة العمل):**
لا ضبط لمعدل طلبات التوقيع (كل غرفة تنطلق فوراً ← ازدحام لحظي عند الذروة)، مزود واحد بلا بديل (`createEulerClient()` نسخة عامة مخبّأة)،
مهلة إغلاق 5ث بعد خروج الستريمر (الريفرش = طلب توقيع جديد)، لا مهلة على طلب التوقيع نفسه، ولا حاجز يمنع اتصالين لنفس اليوزر أثناء الإغلاق والفتح.

**لا يمكن إثباته من هنا:** هل مفتاحك مضبوط وصالح على Render، وما حدود Euler الفعلية لخطتك، وهل يحجب تيك توك IP الخاص بـRender.

## 4) ما لم يُختبر فعلياً
- اتصال ببث تيك توك حقيقي، وسلوك Euler الحقيقي تحت الحمل، وحدود خطتك (الشبكة محجوبة ببيئة العمل).
- بروكسيات حقيقية (اختُبر المسار عبر بروكسي CONNECT محلي فقط: طلب التوقيع والويب سوكيت). جلب رقم الغرفة من صفحة تيك توك عبر البروكسي (got) مربوط لكنه غير مُختبَر.
- عدم تكرار الاتصال بين السيرفرين (الأساسي والاحتياطي) — كل سيرفر مستقل ولا حالة مشتركة بينهما؛ الواجهة تتصل بواحد بوقت واحد.

## 5) تحديث لاحق: مفاتيح متسلسلة، شاشة الفشل، التشخيص

- **مفاتيح API الإضافية (حتى 7 وأكثر):** `EULER_API_KEY` (الأول) + `EULER_API_KEYS=k2,k3,k4,k5,k6,k7`. الاستراتيجية الافتراضية **متسلسلة**:
  الأول وحده يخدم ما دام سليماً، ولو "خلص" (429 أو 402 أو تعطّل) ينتقل الاتصال تلقائياً للثاني ثم الثالث…، ويرجع للأول أول ما يتعافى.
  `TIKTOK_KEY_STRATEGY=balanced` لتقاسم الحمل بالتساوي بدلاً من التسلسل. حالة كل مفتاح (`active` / `standby` / `cooling`) بـ`/health`،
  وباللوغ `event=provider_down … next=` و`event=provider_recovered`. مُختبَر بسبعة مفاتيح (63 فحص تكامل).
- **إصلاح خطأ بالواجهة:** `tiktokOpenWS` كانت تُسقط حقول التقدّم (محاولة/طابور/عدّ تنازلي) فيظهر "محاولة رقم 1" دائماً. صارت تمرّرها،
  والاختبار صار يطلب أرقاماً حقيقية (موقع الطابور، العدّ التنازلي).
- **شاشة الفشل:** تحمل رمز السبب `[sign_failed]` وأمثاله، وتنبّه لو سيرفر Render ما زال على النسخة القديمة (لا يرسل `srv`) — وهو أشيع سبب
  لظهور "تعذّر الربط بعد عدة محاولات" مع موقع جديد وسيرفر قديم.
- **`/diag?token=`** (يعمل فقط لو ضبطت `BRIDGE_DIAG_TOKEN`): آخر أعطال الاتصال بأسبابها الحقيقية (بلا مفاتيح). `TIKTOK_FETCH_ROOM_INFO=0` لتجاوز فحص room/info للتشخيص.
